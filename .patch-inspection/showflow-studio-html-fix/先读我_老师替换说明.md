# ShowFlow 原主题入口：HTML 双屏联动源码修复包

适配依据：本次提供的 `pptist_sync-feature-virtual-show-flow.zip` 根目录源码。

**这是源码增量替换包，不是已经编译好的 dist，也不是先前错误修改 /upload、/play 的升级包。必须重新构建前端。** 保留原工程，在其上应用本包，不要删除整个旧工程后只剩本包。

## 1. 改在哪里，保留什么

在原 `/studio/theme` 的同一个文件选择入口、同一个主题列表中，增加 `.html/.htm`；原 CSS `.zip` 仍保留。继续使用原「设为 Draft → 右侧预览 → 发布 Draft」流程，没有另建 HTML 管理区。

发布后的 HTML 承载在原副屏 `/reveal/` 中。ShowFlow 原主屏 PPT、PPT 上传/播放入口、虚拟步骤编排、WebSocket 角色和消息类型继续使用原机制；没有将 `/play` 改成 PPT/HTML 二选一。核心 Controller、WebSocket 服务器、LCD Payload 类型与 MQTT 发布代码未改。

新增服务器处理负责原主题库里的 HTML 原文、稳定页面清单和运行副本。运行副本放入无同源权限的 iframe；桥接脚本将原 NAVIGATE/SYNC_STATE 转成 HTML 控制接口，在页面渲染后回 ACK。原 HTML 下载内容保持字节一致。

HTML 草稿预览不连接联动 WebSocket，也不会占用正式副屏或向 LCD 发任务。原 CSS 草稿/缩略图预览也增加了相同隔离保护。

## 2. 替换前先备份

暂停现场联动并停止旧服务。先备份正在使用的完整 `data/`、环境配置、原 `dist/` 和工程；使用自定义数据目录时也一并备份。保留浏览器中的原 ShowFlow 数据，不要清空浏览器存储，建议在编排页另存一份原方案。

安装脚本会另做一次**源码备份**，但不会代替上述数据及旧 dist 备份。不要把本包里的 `待上传HTML` 复制为应用的 `index.html`。

若之前装过错误的「PPTist HTML 上传与播放升级包」，先按其备份恢复，或用最新 feature 分支的干净源码副本重新制作部署包。本包检测到不一致会停止，不会强行覆盖。

## 3. 把源码替换到正确位置

将本包解压为 `showflow-studio-html-fix`，在该文件夹打开终端。目标必须是最新工程根目录：同时包含 `src/`、`server/`、`package.json`。**不能指向 `deploy/pptist/`，也不能指向旧的 pptist_sync-main 分支。**

例：两个文件夹位于同一个目录：

```text
工作目录/
├── pptist_sync-feature-virtual-show-flow/  原最新工程
└── showflow-studio-html-fix/               本修复包
```

先只检查，再应用：

```bash
node apply-showflow-html.mjs "../pptist_sync-feature-virtual-show-flow" --check
node apply-showflow-html.mjs "../pptist_sync-feature-virtual-show-flow"
```

脚本会核对原文件 SHA256，备份后替换 7 个已有源码文件并新增 5 个文件（含测试）。`data/`、`dist/`、`deploy/`、`node_modules/`、配置不在写入范围。重复运行会识别已应用，不会重复叠加代码。

若报告「版本不一致」，表示目标不是本次审核的那份源码，或老师另有修改。此时尚未修改文件；可对照 `changes.diff` 人工合并，不能绕过校验硬覆盖。

## 4. 必须构建后再运行

进入目标工程根目录：

```bash
cd ../pptist_sync-feature-virtual-show-flow
```

已有完整依赖且锁文件未变时不必重新安装；首次安装或依赖不完整时执行：

```bash
npm ci
```

然后执行：

```bash
npm run build
```

**必须等待类型检查和构建都成功。失败时停止部署，不要把旧 dist 当作新版启动。** 本包没有增加 npm 依赖，继续使用工程原 package.json/package-lock.json。

### 直接在源码根目录运行

按原方式停止旧服务，然后：

```bash
npm run server
```

端口、数据目录和环境变量继续沿用老师原配置。浏览器刷新 Studio 页面；有旧缓存时强制刷新。

### 部署在 RK3588 / Linux 的情况

先在开发电脑的上述根源码上应用修复并通过 `npm run build`，然后使用老师原来的打包流程**重新生成部署包**。这份源码的 `scripts/build-rk3588-deploy.ps1` 会从根目录复制新的 `server/`、`reveal-example/` 和构建后的 `dist/`，不能直接用压缩包中原来的旧 `deploy/pptist/server` 去覆盖服务器。

老师原打包脚本有自己的 Node ARM64 运行时和依赖准备步骤；继续使用其已有环境。本修复包不另附运行时、依赖或字体文件。

升级运行目录时，新 `server/`（包含全部四个新增 runtime 文件）、`dist/`、副屏 `showflow.js` 要来自同一次构建；**保留现有 data、配置和运行脚本**。使用原安全升级/重启方式，不要执行会清空 data 的整目录替换。

## 5. 现在按原位置上传

1. 打开原 `/studio/theme`。仍然是「页面主题」，不是 PPT 上传界面。
2. 在原文件选择框选择 `待上传HTML/智证先锋_16页无汽车首页版.html`。
3. 上传完成后，主题列表应显示「HTML 页面 · 16 页」。上传本身不会切换正式内容。
4. 点击该项「设为 Draft」，右侧应出现已确认的蓝色流程网页。预览可以选择画面、翻页，车端联调页应有两位工程师共同高亮。
5. 确认后点击顶部「发布 Draft」。主屏 PPT 不改变。
6. 新打开的原副屏 `/reveal/` 使用已发布内容；正在打开的 HTML 副屏会提示有新版，但不会强制跳页。正式切换前由操作员载入新版或刷新副屏。

只上传 HTML，不上传截图，不把 HTML 压成原 CSS 主题 ZIP。原 CSS ZIP 的安全规则仍不允许 HTML/JS 混入。

## 6. 第一次把 HTML 接入双屏编排（重要）

在原 `/showflow` 中保留 PPT 主屏，副屏选择「Studio 页面（CSS / HTML）」。使用原 Studio 内容地址：

```text
/api/studio/slides/active/raw
```

这个地址仍是内容源标识；新适配器会先读取已发布的 HTML 页面清单，无需把它改成上传文件路径。

**先另存原方案，再刷新副屏页面池，逐步核对绑定。** 最终 HTML 也有 16 个画面，但它与老师旧 Markdown 的 16 页不是同一套稳定 ID，不能按第几页直接替换。修复后会保留旧编排并提示待重新绑定，而不是自动删除旧副屏引用。

以 `HTML_16页稳定ID目录.md` 为准，将对应画面放到需要的虚拟步骤里。PPT 连续讲多个页面时，副屏可以选「保持当前」，不必跟着每一页跳。工作环节结束时再选择相应总览页；车端联调详情使用 `stage-1-detail-1`。

最后打开原副屏 `/reveal/`，由 ShowFlow 控制台执行前进、后退、跳步。HTML 端按稳定 ID 跳转，并在切换后回 ACK；找不到 ID 时会返回错误，不会用随便一页冒充成功。

同一个会话只保留需要的正式副屏窗口，其他同源正式 `/reveal/` 窗口也会作为副屏接收指令。Studio 草稿窗口不参与。

## 7. 页面与数据边界

- 已确认 HTML 原文没有改动：首页无汽车、仅显示职称、16 页、车端联调双岗高亮保留。
- 支持自包含 UTF-8 HTML，32 MiB 上限。图片、样式和脚本应内嵌；不支持依赖外网 CDN、相对资源目录、摄像头或任意外部 API 的网页。
- 这份智证先锋 HTML 自动从 `flow-data` 的 JSON 识别多页，不在服务器运行上传脚本。普通无控制接口的 HTML 只按单页处理，不虚构页数。
- 新 HTML 使用原 `data/studio/themes/` 主题库；上传、Draft、Active、发布历史仍由 Studio 管理。重新上传同名 HTML 是独立不可变版本，旧主题保留以便回退。
- HTML 自带内容与照片；在 Studio「页面内容」里修改 Markdown 或原头像，不会自动改写 HTML。更新 HTML 后回到主题入口重新上传。
- LCD 继续走原 schema/渲染/发布机制；详情页可从清单提取原四岗任务信息。HTML 里的动态岗位点击并不自动产生新的真实设备数据。外部设备现场状态仍需原平台验证。
- 上传管理仍沿用老师系统原权限边界，本包没有替整个系统新增登录鉴权，只应在可信局域网使用，不应直接暴露公网。
